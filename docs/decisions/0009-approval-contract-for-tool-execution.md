# ADR-0009: approval contract สำหรับการเรียก tool — ใบอนุมัติผูกกับอะไร และใครเป็นผู้มีอำนาจได้

**Status:** Proposed
**Date:** 2026-10-12
**Depends on:** ADR-0001 · ADR-0003 · ADR-0005
**Blocking:** เส้น write/privileged ของ runtime 🔒 · ADR-0007 (เกณฑ์วัด)
**Supersedes:** —
**Related ws-001:** `dec-f7cbd10c` เกณฑ์ 7 · `dis-a84b7a8e` seq 6 · `dis-514ae7a7` seq 7 · seq 13 · `dis-58a707ef` seq 29

## Context

รีโปนี้ถือ **approval contract** ตามขอบเขตที่ใบ boundary กำหนด และเป็นหนี้ชิ้นเดียวที่เป็นของใหม่จริง —
เส้น write/privileged ของ runtime 🔒 ติดอยู่กับมันตั้งแต่ 17 ก.ย. 2026

**สิ่งที่มีอยู่แล้วและห้ามเขียนทับ** — `approval/v1` ของ `agent-platform` (semantics เป็นของ `devfactory-core` RFC-0002)

```
required     approval_id · tenant_id · subject{type,id} · decision · reason · authority · decided_at
optional     workspace_id · execution_id · agent_id · policy_id · action_risk · expires_at
             escalation_target · correlation_id · supersedes_approval_id
Decision     APPROVE · REJECT · REQUIRE_CHANGES      ชุดปิด เพิ่มค่าต้องมี RFC ที่ต้นทาง
guarantees   1 decision immutable — เปลี่ยนใจ = ใบใหม่ที่อ้างใบเดิม
             2 ทุก APPROVE ต้องมี event คู่กัน
             3 execution ที่ไม่มี APPROVE เป็นสิ่งที่ห้าม
             4 REQUIRE_CHANGES ไม่ใช่ REJECT
```

✅ **หลายข้อที่เราเคยเรียกร้อง ถูกปิดไปแล้วที่ต้นทาง ไม่ต้องขอซ้ำ** — ไม่มี `AUTO_APPROVE` โดยเจตนา
(คำอธิบายในไฟล์ระบุเองว่าการเพิ่มค่าแบบนั้น *"เปิดทางให้ execution เดินโดยไม่มี APPROVE ของคนได้ด้วยการเพิ่มค่า ไม่ใช่การลบค่า"*)
· `expires_at` ระบุว่าใบหมดอายุใช้เดินงานไม่ได้ และงานที่ค้างควรเข้า timeout · `supersedes_approval_id` รองรับการเปลี่ยนใจ
· `execution/v1` มี `awaiting_approval` + `approval_id` พร้อม invariant ที่ JSON Schema ตรวจให้ไม่ได้

🔴 **สองช่องที่ยังไม่มี และเป็นเหตุของใบนี้**

**ช่องที่หนึ่ง — ทุกช่องที่ผูกใบเข้ากับงาน เป็น id ล้วน ๆ**

`subject.id` · `execution_id` · `policy_id` · `correlation_id` — **ไม่มีช่องใดผูกกับเนื้อของสิ่งที่จะรันจริง**

ผลที่ `care-agent-platform` พิสูจน์จาก production ของเขาเอง (`dis-a84b7a8e` seq 6):

> ใบที่อนุมัติ `reboot node A` ถูกเอาไปรันคำสั่งอื่นบน node B ได้ ถ้า implementation ผูกใบด้วย id

**ช่องที่สอง — guarantee ข้อ 3 ไม่ได้บอกว่า APPROVE ต้องมีผู้มีอำนาจที่พิสูจน์ได้**

ในวงนี้ความเป็น "คน" ถูกอ้างผ่าน static bearer + ชื่อที่ผู้เรียกประกาศ (ADR-0001)
**วันนี้ guarantee 3 จึงผ่านได้ด้วยใบที่ไม่มีใครยืนยันตัวผู้อนุมัติ**

✅ และวงนี้แก้ปัญหาเดียวกันที่ชั้นอื่นไปแล้ว — ระบบ coordination บันทึกความแข็งของผู้ตัดสินเป็น `human` หรือ `relayed`
พร้อมข้อความ *"ตามที่ผู้ใช้สั่งผ่านไคลเอนต์ ยังไม่ได้ยืนยัน"* เมื่อไม่มีรหัสยืนยัน · **รูปนั้นใช้ได้ที่นี่เหมือนกัน**

## Options

### A. ชั้นบน `approval/v1` — invariant ของผู้ผลิต + ขอ field ระดับ platform หนึ่งช่อง (แนะนำ)

* ✅ ไม่สร้างสัญญาคู่ขนาน ซึ่ง `dec-86445c19` ข้อ 2 ห้ามไว้
* ✅ มีแบบอย่างชัด: `correlation_id` ถูกเพิ่มเป็น **field ระดับ platform ตาม ADR-0006 กฎข้อ 1** โดย *"เพิ่มได้เองโดยไม่ต้องมี RFC ที่ repo ต้นทาง · guarantees ไม่ขยับ"*
* ❌ ต้องรอ `agent-platform` รับ field ก่อนบังคับได้เต็ม

### B. เก็บ digest ไว้ในเรคอร์ดของ runtime เอง

* ✅ ทำได้ทันที ไม่ต้องรอใคร
* ❌ ได้เรคอร์ดที่สองที่พูดเรื่องเดียวกับใบอนุมัติ แล้วเพี้ยนจากกันภายในเดือนเดียว — รูปที่วงนี้ปิดมาหลายรอบ

### C. ยัด digest ลง `subject.id`

* ✅ ไม่ต้องเพิ่มช่อง
* ❌ `subject` คือ *สิ่งที่ถูกอนุมัติ* ตาม ADR-0017 ของต้นทาง · ใส่ digest ทำให้ id ไม่ชี้ของจริง และ `supersedes` เทียบ subject ไม่ได้

## Decision

**A** — ใบนี้ไม่เขียนสคีมาใหม่ · มันเขียน **invariant ที่ผู้ผลิตต้องบังคับเอง** ซึ่ง `approval/v1` ระบุเองว่า JSON Schema ตรวจให้ไม่ได้

### 1 · ใบอนุมัติต้องผูกกับ *เนื้อ* ไม่ใช่แค่ *id*

```
subject          tool_call หรือ execution ที่จะรัน   (ค่าตาม SubjectType ของต้นทาง)
payload digest   ลายนิ้วมือของสิ่งที่จะรันจริง          ← ช่องที่ยังไม่มี
target           ของที่คำสั่งไปลง                     (ADR-0005)
```

**digest คิดจาก** ชื่อ tool + argument ที่ normalize แล้ว + target · เรียงคีย์ตายตัว · ไม่รวมเวลา ไม่รวม request id
**ถ้า digest ของสิ่งที่กำลังจะรันไม่ตรงกับที่ใบผูกไว้ ให้ปฏิเสธ** ไม่ใช่รันแล้วบันทึกว่าต่าง

> **ใบที่ผูกด้วย id อนุมัติ *คำขอ* · ใบที่ผูกด้วย digest อนุมัติ *สิ่งที่จะเกิดขึ้น***
> สองอย่างนี้ต่างกันทันทีที่ argument เปลี่ยนระหว่างทาง

**ข้อเสนอต่อ `agent-platform`:** เพิ่ม field ระดับ platform หนึ่งช่องใน `approval/v1` สำหรับ digest (ชื่อเป็นของเขาตัดสิน)
อ้างแบบอย่าง `correlation_id` · **จนกว่าช่องนั้นจะมี เส้น write/privileged ยังไม่เปิด** ไม่ใช่เปิดแล้วผูกด้วย id ไปก่อน

### 2 · ความแข็งของผู้มีอำนาจต้องถูกบันทึก ไม่ใช่ถูกสมมติ

เอากฎ ADR-0003 มาใช้กับช่อง `authority` ตรง ๆ

```
verified   ยืนยันด้วยกลไกที่พิสูจน์ได้
relayed    มีคนสั่งผ่านไคลเอนต์ แต่ยังไม่มีอะไรยืนยัน
```

**ห้ามเว้นว่าง ห้ามสมมติว่า verified** · ยืมรูปจากระบบ coordination ที่ใช้ `human`/`relayed` อยู่แล้วและทำงานได้จริง

**และก่อนเปิด write/privileged: ใบที่ผู้มีอำนาจเป็น `relayed` ไม่นับว่าสอดคล้อง guarantee ข้อ 3**
— ไม่ใช่เพราะใบนั้นปลอม แต่เพราะ guarantee 3 มีไว้กัน execution ที่ไม่มีคนอนุมัติ
และใบที่ยืนยันตัวคนไม่ได้ **ก็ยังไม่ได้พิสูจน์ว่ามีคนอนุมัติ**

### 3 · ผู้ยื่นตัดสินคำขอของตัวเองไม่ได้ — บังคับด้วยโครงสร้าง

เทียบผู้มีอำนาจกับผู้ยื่น ปฏิเสธถ้าเป็นตัวเดียวกัน · ผู้มีอำนาจต้องเป็นคน

**ข้อนี้สำคัญกับ gateway มากกว่าโดเมนอื่น** เพราะผู้ขอคือ AI และผู้อนุมัติที่สะดวกที่สุดคือ AI อีกตัว
· `care-agent-platform` บังคับด้วยโค้ดบน production แล้ว

> ถ้าไม่บังคับด้วยโครงสร้าง กติกา "ไม่ใช่ AI อนุมัติแทนกัน" จะเป็นแค่ข้อความในเอกสาร

### 4 · การสั่งหยุด ห้ามติดคิวอนุมัติ ไม่ว่ากรณีใด

> คิวอนุมัติบนเส้นหยุด แปลว่าทางเดียวที่จะหยุดของที่กำลังทำผิด คือรออนุญาต

### 5 · คนต้องเห็นคิวได้โดยไม่ต้องเปิด session ค้าง

ต้องตอบได้ว่า **คนเห็นคิวจากที่ไหน** · โอเปอเรเตอร์ไม่ได้เฝ้าหน้าจอ AI ไว้

### 6 · "ยกเลิกเพราะเรื่องจบไปทางอื่น" ไม่ใช่ decision — ไม่ต้องเพิ่มค่าใน enum

map ลง `execution/v1` `ExecutionState` → `cancelled` **และไม่สร้างเรคอร์ด approval เลย**
· ถ้าปล่อยให้การถอนไปแตะตารางคำตัดสิน บันทึกจะบอกว่ามีคนอนุมัติทั้งที่ไม่มีใครตัดสินอะไร

### 7 · ใบหมดอายุทำให้งาน *หยุด* ไม่ใช่ *เดิน*

`expires_at` ของต้นทางเขียนถูกแล้ว · ยกมาเป็นเกณฑ์เพราะ **ทางลัดที่ทุกคนอยากทำเมื่อคิวค้างคือ
"ครบเวลาแล้วอนุมัติให้เลย"** ซึ่งแปลว่าเวลาที่ผ่านไปกลายเป็นผู้มีอำนาจ

> การรอนานคือความไม่สะดวก · การอนุมัติเองคือความเสียหายที่ย้อนไม่ได้

**Authority:** — `Proposed` · ข้อ 1 ต้องให้ `agent-platform` รับ field ก่อนบังคับได้เต็ม · ข้อ 2–7 บังคับได้เลยโดยไม่แก้สัญญาต้นทาง

## Consequences

* **เส้น write/privileged ยังไม่เปิด** จนกว่าข้อ 1 มีช่องให้ผูก และข้อ 2–5 มีของจริง — ประกาศตรง ๆ ดีกว่าเปิดแล้วผูกด้วย id
* `agent-platform` ได้คำขอหนึ่งข้อที่ชัดและมีแบบอย่าง (field ระดับ platform แบบ `correlation_id`)
* ผู้ผลิตใบต้องเก็บ **ผู้ยื่น** ไว้เทียบกับผู้มีอำนาจ — ไม่เก็บ = ข้อ 3 บังคับไม่ได้
* เกณฑ์ที่วัดได้อยู่ที่ [`conformance/approval/CRITERIA.md`](../../conformance/approval/CRITERIA.md) ตาม ADR-0007
* **ไม่มีสคีมาใหม่ในรีโปนี้** — `approval/v1` ยังเป็นเจ้าของรูปของเรคอร์ด

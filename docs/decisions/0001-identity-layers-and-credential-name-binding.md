# ADR-0001: identity สามชั้น และการผูกชั้น credential กับชื่อที่ผู้เรียกประกาศ

**Status:** Proposed
**Date:** 2026-10-12
**Depends on:** —
**Blocking:** ADR-0002 · approval contract (ยังไม่เขียน)
**Supersedes:** —
**Related ws-001:** `dis-a84b7a8e` seq 13–14 · `dec-4e9b685e` (proposed) · `dis-3b5cb137` seq 84 · `dec-f7bdf7fa`

## Context

ระบบในวงนี้แยกตัวตนออกเป็นชั้น ๆ มาตั้งแต่ ก.ย. 2026 แต่คำนิยามอยู่กระจัดกระจายในกระทู้สองที่
และมีใบที่เสนอรูปสามชั้นอยู่ (`dec-4e9b685e`) ซึ่งยัง `proposed` และมีทีม consumer รออยู่เพื่อเขียนเกณฑ์วัด

✅ **หลักฐานที่พิสูจน์แล้ว ไม่ใช่การคาดการณ์** — `trueforge-poc` ข้อค้นพบ 1: โทเคนใบเดียว ส่งชื่อที่ประกาศเอง
ต่างกันสามครั้ง ได้ตัวตนสามค่า **รวมชื่อที่แต่งขึ้นเอง**

✅ ที่ `dis-a84b7a8e` seq 13 วงนี้สรุปรูปไว้แล้วว่า token คือกุญแจ · **รายการชื่อในใบ token คือขอบเขตว่าอ้างชื่อไหนได้**
· ชื่อที่ส่งมาแต่ละครั้งคือค่าที่เลือกจากขอบเขตนั้น · และ seq 14 ปิดท้ายว่าถ้าไม่ส่งชื่อแล้วใบมีหลายชื่อ **ควรปฏิเสธ**

🟡 `dec-4e9b685e` ได้สองชั้นเดียวกันโดยไม่ได้ลอกกัน และเพิ่มชั้นที่สาม (บริบทของงาน) ซึ่งยังไม่มีตอนนั้น
**แต่ไม่มีแนวคิดเรื่องขอบเขต** — ตามตัวอักษรแล้วผู้ถือ credential ประกาศเป็นชื่อใดก็ได้

เหตุที่ต้องตัดสินตอนนี้: `dec-bdbba540` (proposed คู่กัน) เสนอให้ใช้ค่าชั้นที่สองนี้ทำ **routing**
· attribution ที่เชื่อไม่ได้คือความน่ารำคาญ · **routing ที่เชื่อไม่ได้คือการส่งงานในนามคนอื่นได้**

## Options

### A. ผูกขอบเขต — credential ประกาศไว้ว่าอ้างค่าชั้น 2 อะไรได้บ้าง (แนะนำ)

* ✅ ปิดช่องปลอมที่พิสูจน์แล้วว่าเกิดจริง โดยไม่ต้องรอ OAuth
* ✅ กฎของ ก.ย. และของ `dec-4e9b685e` ประกอบกันได้ครบสี่กรณีโดยไม่ขัดกันเอง
* ✅ เพิ่มข้อเดียว ไม่เปลี่ยนความหมายของช่องเดิม
* ❌ ต้องมีที่เก็บว่าใบไหนอ้างชื่อไหนได้ ซึ่งวันนี้ยังไม่มี

### B. คงตามใบ — ชั้น 2 ไม่ให้อำนาจ แต่ประกาศเป็นชื่อใดก็ได้

* ✅ ไม่ต้องทำอะไรเพิ่ม
* ❌ บันทึก attribution ปลอมได้ และ `dec-bdbba540` จะ route บนค่าที่ปลอมได้
* ❌ ขัดกับ `dis-a84b7a8e` seq 13–14 ที่วงนี้เคยสรุปไว้แล้ว โดยไม่มีใบไหนถอนข้อนั้น

### C. ปฏิเสธทุกครั้งที่ไม่ส่งชื่อ (ตามตัวอักษรของ ก.ย.)

* ✅ ไม่มีแถวใดในบันทึกที่ตัวตนกำกวม
* ❌ งานหยุดเมื่อผู้เรียกลืมส่งชื่อ ทั้งที่การบันทึกว่า "แยกไม่ได้" ก็พูดความจริงได้
* ❌ ขัดกับเกณฑ์ 2ก ของ `dec-f7cbd10c` ที่อนุมัติแล้ว ซึ่งเลือก *บันทึกว่าแยกไม่ได้* แทนการหยุด

## Decision

**A** — สามชั้นตาม `dec-4e9b685e` **บวกการผูกชั้น 1 กับชั้น 2**

```
ชั้น 1  credential / principal    ควบคุมการเข้าถึง
ชั้น 2  ชื่อที่ผู้เรียกประกาศ        attribution เท่านั้น · ห้ามให้อำนาจ
ชั้น 3  บริบทของงาน (acting_context)  ไม่ใช่ทั้งกุญแจและไม่ใช่ทั้งชื่อ
```

**ขอบเขต:** credential แต่ละใบประกาศไว้ว่าอ้างค่าชั้น 2 อะไรได้บ้าง

```
ส่งชื่อ · อยู่ในชุด        →  ใช้ชื่อนั้น
ส่งชื่อ · อยู่นอกชุด        →  ปฏิเสธ ไม่ใช่บันทึก          ← ข้อที่เพิ่ม
ไม่ส่งชื่อ · ใบมีชื่อเดียว    →  ใช้ชื่อนั้น
ไม่ส่งชื่อ · ใบมีหลายชื่อ    →  ค่าที่อ่านออกว่าแยกไม่ได้      ← ตาม dec-4e9b685e และ ADR-0003
```

**Reason:** แถวที่สองเป็นแถวเดียวที่กันการปลอม และเป็นแถวที่ `dec-4e9b685e` ไม่มี
แถวที่สี่เป็นข้อที่ใบนั้นดีกว่าของ ก.ย. เพราะบันทึกยังพูดความจริงและงานยังเดิน
**ชั้น 2 ยังไม่ให้อำนาจในทุกกรณี** การผูกขอบเขตเป็นเรื่องความถูกต้องของบันทึก ไม่ใช่การเลื่อนชั้น 2 ขึ้นเป็นสิทธิ์

**Authority:** — ยังไม่มีผู้อนุมัติ · ใบนี้เป็น `Proposed` จนกว่า `dec-4e9b685e` จะถูกเคาะและเจ้าของงานรับข้อที่เพิ่ม

## Consequences

* รูปของ credential ต้องมีที่เก็บรายการชื่อที่อนุญาต — เป็นงานของผู้ถือ credential store ไม่ใช่ของรีโปนี้
* ผู้บริโภคที่ route บนค่าชั้น 2 (`dec-bdbba540`) ต้องรอขอบเขตนี้ ไม่ใช่ route ก่อนแล้วผูกทีหลัง
* `identity_note` ที่ `dec-4e9b685e` คงไว้เพื่อ backward compatibility กลายเป็นสัญญาณที่สองสำหรับเงื่อนไขเดียว
  — ต้องมีบรรทัดระบุว่าช่องไหนเป็นคำตอบ ดู ADR-0003
* **ไม่กระทบ** ความหมายของช่องใดในวันนี้ จึงไม่ต้องแก้ของเดิมก่อนใบผ่าน
